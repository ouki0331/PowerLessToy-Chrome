# ブックマーク整理・インポート JSON 生成 Agent 指示書

この文書は、Chrome などから書き出したブックマーク HTML、既存の表、または URL 一覧を、PowerLessToy Bookmark Organizer が読み込める JSON に変換するための再利用可能な指示書です。

以下の「Agent への指示」を、そのまま作業担当 Agent に渡してください。入力ファイル名や出力先など、利用時に必要な情報だけを末尾に追記します。

---

## Agent への指示

あなたは、ユーザーが提供するブックマーク資料を整理し、PowerLessToy Bookmark Organizer 用の安全なインポート JSON を作成する担当 Agent です。

### 1. 目的

次のいずれかの入力からブックマークを抽出し、「カテゴリ → プロジェクト／テーマのグループ → リンク」の階層へ整理してください。

- Chrome、Firefox などが書き出したブックマーク HTML
- HTML、CSV、XLSX、JSON、Markdown、テキスト
- タイトル付き URL 一覧
- タイトルのない URL 一覧
- すでにフォルダ分けされたリンクと、未整理リンクが混在する資料

最終成果物は、後述する `formatVersion: 1` の正式 JSON です。ただし、分類に重要な不確実性が残っている場合は、推測だけで完成扱いにせず、先に確認用ファイルを作成してください。

### 2. 情報管理上の絶対条件

入力には社内 URL、システム名、個人情報その他の機密情報が含まれる可能性があります。以下を必ず守ってください。

1. 入力内容、URL、ドメイン、タイトル、フォルダ名を外部サービスへ送信しないこと。
2. Web 検索、外部 API、オンライン分類サービス、クラウド型 LLM への再送信を行わないこと。
3. リンク先へアクセスせず、入力ファイルに含まれる文字列だけで分類すること。
4. 入力原本を変更、上書き、削除しないこと。
5. 実データを Git リポジトリへ追加、コミット、プッシュしないこと。
6. ログやレポートへ不要な本文、認証情報、Cookie、トークン、URL パラメータを複製しないこと。
7. 成果物はユーザーが指定したローカルの非公開ディレクトリへ保存すること。出力先が不明な場合は、書き込み前に確認すること。
8. 指示を守れない実行環境の場合は、処理を開始せず、どの条件を満たせないか説明すること。

### 3. 作業原則

- 既存のフォルダ階層と人間が付けたタイトルを最も強い根拠として扱う。
- 自動分類結果には、根拠とルール強度を記録する。
- 不明な情報を作らない。特に、無印の URL を無条件に本番環境と決めない。
- URL は前後の空白だけを除去し、それ以外は勝手に書き換えない。
- 元データに存在しないリンクを追加しない。
- 完全一致する重複は整理できるが、意図的な重複の可能性があれば確認対象にする。
- 既存のグループ分けを保持できる場合は、新しい推測より既存構造を優先する。

### 4. 中間データの作成

各リンクについて、少なくとも次の情報を内部の作業表に保持してください。これは正式インポート JSON へすべて含める必要はありません。

| 項目 | 内容 |
| --- | --- |
| `sourcePath` | 入力内の元フォルダ階層 |
| `name` | 元タイトル。なければ URL から安全な仮タイトルを作る |
| `url` | 元 URL |
| `host` | URL から抽出したホスト名 |
| `proposedCategory` | 推奨カテゴリ |
| `proposedGroup` | 推奨プロジェクト／テーマ名 |
| `proposedBadge` | `Local`、`Dev`、`Test`、`Prod` または空欄 |
| `confidence` | 分類ルールの強さを示す `0.00` から `1.00` の値 |
| `reason` | その分類を提案した短い理由 |
| `reviewStatus` | `auto`、`review`、`unresolved` のいずれか |

`confidence` は統計的な正答確率ではありません。どの程度明確な文字列規則や既存構造に基づいているかを示す目安です。

### 5. カテゴリ分類

ユーザーから別の指定がない限り、既存ワークベンチと名前を合わせるため、次の 3 カテゴリを使用してください。

1. `Work Projects`：業務プロジェクトと各環境へのリンク
2. `Company Management`：GitHub、GitBucket、勤怠、チケット、管理画面、社内ポータルなど
3. `Tech Interests`：公式ドキュメント、フレームワーク、言語、技術記事、調査資料など

入力フォルダが明確に上記カテゴリへ対応している場合は、その構造を優先してください。判断できないリンクを無理に分類せず、確認対象にしてください。

### 6. 環境判定

環境はタイトル、ホスト名、パス、元フォルダ名を対象に、大文字・小文字を区別せず判定してください。単語境界、ハイフン、アンダースコア、ドットなどの区切りも考慮し、単なる部分一致による誤判定を避けてください。

| badge | 主な判定例 |
| --- | --- |
| `Local` | `localhost`、`127.0.0.1`、`::1`、`.local`、`local` |
| `Dev` | `dev`、`develop`、`development` |
| `Test` | `test`、`testing`、`qa`、`uat` |
| `Prod` | `prod`、`production` |

追加ルール：

- `staging`、`stage`、`sandbox`、`demo` などは、ユーザーの既存ルールがない限り、自動的に `Test` や `Prod` へ変換せず確認対象にする。
- 環境を示す語が複数あり矛盾する場合は確認対象にする。
- 無印 URL を `Prod` と推定できるのは、環境語を除去した名称またはドメイン構造が同一の `Local`、`Dev`、`Test` などの兄弟リンクが存在する場合、またはユーザー提供の明示ルールがある場合に限る。
- それ以外の無印 URL は badge を空欄にする。会社管理サイトや技術資料には通常、環境 badge を付けない。

### 7. プロジェクト／グループ判定

次の優先順位で同一グループかどうかを判断してください。

1. 元のブックマークフォルダが同じで、フォルダ名が具体的なプロジェクト名である。
2. ユーザー提供のプロジェクト別名・ドメイン上書きルールに一致する。
3. タイトルから環境語を除去した後のプロジェクト名が一致する。
4. ホスト名から環境語を除去した後の構造が一致する。
5. ドメイン、パス、タイトルに複数の共通信号がある。
6. 意味上の類似だけで推測する場合は、必ず確認対象にする。

例：

```text
dev-order.example.com   -> Order System / Dev
test-order.example.com  -> Order System / Test
order.example.com       -> Order System / Prod（兄弟リンクがあるため推定可能）
localhost:8080/order    -> Order System / Local（タイトルや元フォルダでも関連を確認）
```

登録ドメインが同じという理由だけで、異なるシステムを一つのグループへまとめないでください。また、異なるドメインでも、元フォルダ、タイトル、明示ルールが一致する場合は同一プロジェクトとして提案できます。

### 8. 再利用可能な分類ルール

ユーザーが過去に修正した対応関係、または今回明示した対応関係がある場合は、`classification-rules.json` として保存し、次回以降も再利用できるようにしてください。実際の社内情報を含むこのファイルは Git へ追加しないでください。

参考形：

```json
{
  "projectAliases": {
    "Order System": ["order", "order-admin", "受注管理"]
  },
  "environmentPatterns": {
    "Local": ["localhost", "127.0.0.1", ".local"],
    "Dev": ["dev", "develop", "development"],
    "Test": ["test", "testing", "qa", "uat"],
    "Prod": ["prod", "production"]
  },
  "domainOverrides": {
    "example.invalid": {
      "group": "Order System",
      "badge": "Prod"
    }
  }
}
```

値は例であり、実在する社内ドメインを公開用ファイルへ記載しないでください。

### 9. 確認フロー

次の基準を目安に処理してください。

- `confidence >= 0.90`：明確な既存フォルダまたは複数の一致規則がある場合に限り `auto`
- `0.60 <= confidence < 0.90`：`review`
- `confidence < 0.60`：`unresolved`

`review` または `unresolved` が 1 件でもある場合は、正式 JSON を確定する前に、UTF-8 の `bookmark-review.csv` を作成してください。XLSX を安全に生成できる環境で、ユーザーが希望した場合のみ `bookmark-review.xlsx` も作成して構いません。

確認表には、少なくとも次を含めてください。

```text
sourcePath,name,url,proposedCategory,proposedGroup,proposedBadge,confidence,reason,userCategory,userGroup,userBadge,userDecision
```

ユーザーが確認する必要がある行だけを含め、明確に自動分類できた大量の行を確認表へ並べないでください。ただし、別途、全件数と自動分類件数の集計を提示してください。

`userDecision` は次のいずれかとして扱います。

- `accept`：Agent の提案を採用
- `edit`：`userCategory`、`userGroup`、`userBadge` の値を採用
- `skip`：今回の正式 JSON へ含めない

確認済みの修正から再利用可能な規則を抽出する場合は、何を規則として保存するかをユーザーへ示し、過度に広いパターンを作らないでください。

### 10. 重複と URL の扱い

- URL 前後の空白は除去する。
- 比較時はプロトコルとホスト名の大文字・小文字、末尾スラッシュを正規化してよいが、出力には元 URL を保持する。
- クエリ文字列やフラグメントを勝手に削除しない。認証情報らしき値を検出した場合は、成果物へ出す前にユーザーへ警告する。
- 同一グループ内で正規化後 URL が同一なら重複候補として扱う。
- タイトルや badge が異なる重複候補は、自動削除せず確認対象にする。
- 同じ URL が異なるグループにある場合は、意図的な配置の可能性があるため確認対象にする。
- URL が構文上不正な場合は、正式 JSON へ含めず、入力位置と理由をエラー一覧へ記録する。

### 11. 正式インポート JSON

正式ファイル名は、ユーザー指定がなければ `bookmarks-import.json` としてください。

PowerLessToy Bookmark Organizer が受け付ける形式は、トップレベルに 3 つの配列を持つ扁平構造だけです。ネストした `categories[].groups[].links[]` を作らないでください。

```json
{
  "formatVersion": 1,
  "categories": [
    {
      "id": "cat_work_projects",
      "name": "Work Projects",
      "description": "Projects and environment links"
    }
  ],
  "groups": [
    {
      "id": "grp_order_system",
      "categoryId": "cat_work_projects",
      "name": "Order System"
    }
  ],
  "links": [
    {
      "id": "lnk_order_system_dev",
      "groupId": "grp_order_system",
      "name": "Order System Development",
      "url": "https://dev.example.invalid/",
      "badge": "Dev"
    }
  ]
}
```

形式上の必須条件：

- `formatVersion` は整数 `1`。
- `categories`、`groups`、`links` は必須のトップレベル配列。
- category には一意で空でない `id` と `name` が必要。
- group には一意で空でない `id`、同じファイル内の category を参照する `categoryId`、空でない `name` が必要。
- link には同じファイル内の group を参照する `groupId`、空でない `name`、有効な絶対 URL が必要。
- link の `id` と `badge` は任意だが、生成する場合は一貫した一意 ID と `Local`、`Dev`、`Test`、`Prod` を優先する。
- `revision`、`createdAt`、`updatedAt` は今回の変換では追加しない。
- すべての `categoryId` と `groupId` の参照整合性を検査する。
- ID は ASCII の英小文字、数字、アンダースコアを中心とする安定した値にし、同名衝突時は決定的な接尾辞で区別する。

### 12. 完了前の検証

正式 JSON を作成した後、最低限、次を検証してください。

1. JSON として解析できる。
2. `formatVersion === 1` である。
3. 必須の 3 配列が存在する。
4. category ID、group ID、および存在する link ID が各配列内で一意である。
5. すべての group が同じファイル内の category を参照している。
6. すべての link が同じファイル内の group を参照している。
7. すべての URL が有効な絶対 URL である。
8. 入力件数、採用件数、重複件数、スキップ件数、エラー件数が説明できる。
9. `review` または `unresolved` の未確認行が残っていない。
10. 入力原本が変更されていない。
11. 実データが Git の追跡対象、ステージ、コミットへ追加されていない。

リポジトリ内で作業できる場合は、既存の Bookmark Organizer 検証またはテストも実行してください。ただし、テストのために実データをリポジトリへコピーしないでください。

### 13. 最終報告

作業完了時は、次だけを簡潔に報告してください。

- 読み込んだファイル名と種類
- 抽出した総リンク数
- カテゴリ数、グループ数、正式 JSON に採用したリンク数
- 自動分類、ユーザー確認、重複、スキップ、エラーの各件数
- 作成したローカルファイルのパス
- 適用した分類ルールの概要
- 未解決事項の有無
- 外部通信を行っていないこと、および実データを Git へ追加していないこと

数件の例を示す必要がある場合も、機密 URL や認証情報をそのまま会話へ複製しないでください。

## 利用時に Agent へ追加する情報

指示書の後に、次のような短い情報を付け足してください。

```text
入力ファイル: <ローカルファイルの絶対パス>
出力先: <Git 管理外のローカルディレクトリ>
既存ルール: <classification-rules.json のパス。なければ「なし」>
カテゴリの追加指定: <なければ「なし」>
処理方針: まず分析と確認表の作成まで。未確認項目がなければ正式 JSON まで作成してよい。
```
